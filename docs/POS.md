# Касса магазина (POS)

## Архитектура и решение по ролям

Модуль расширяет существующие ASP.NET Core 8 / EF Core / PostgreSQL и React/Vite в `admin`. Отдельного проекта `admin/web` в репозитории нет: экран расположен в `admin/src/Pos.tsx` и подключён к существующей панели.

Добавлена строковая роль `Cashier` («Кассир»). Старые значения ролей и их права для интернет-заказов сохранены. Новая роль совместима с текущим полем `StaffUser.Role`; изменение схемы сотрудников не требуется. Назначается администратором на экране сотрудников.

| Роль | Продажа / отложенные | Чеки | Возврат POS | Отчёт POS |
|---|---|---|---|---|
| Administrator | Все | Все | Все | Да |
| Cashier | Свои | Свои | По своим чекам | Нет |
| Finance | Нет | Все, просмотр | Нет | Да |
| OrderManager | Нет | Нет | Нет | Нет |
| Support | Нет | Нет | Нет | Нет |

Каждый POS-запрос проверяет активность сотрудника и соответствие роли в JWT текущей роли в БД. Ограничения действуют в API, независимо от скрытых кнопок интерфейса. POS хранится отдельно от интернет-заказов, платежей и возвратов: прежние API менеджера заказов не открывают доступ к кассовым данным.

## Экран и операции

### Кассовые смены

Перед новой продажей или возвратом сотрудник открывает свою смену и указывает начальные наличные. Одновременно допускается одна открытая смена на сотрудника (ограничение БД). Отложенные чеки можно готовить без смены; при проведении они относятся к текущей смене продавца. Старые чеки сохраняются с пустым ShiftId и доступны для возврата в текущей смене.

Кассир видит и закрывает свои смены. Администратор видит и закрывает любые смены. Финансы видят смены и итоги без права открытия/закрытия. Менеджер заказов и поддержка не имеют доступа.

Итоги разделены на наличные, карту и QR: продажи, возвраты и чистая сумма. Ожидаемые наличные = начальные наличные + наличные продажи − наличные возвраты (сдача уже исключена). При закрытии фиксируются фактическая сумма, расхождение, время и закрывший сотрудник. Повтор закрытия с прежней суммой безопасен; изменить сумму закрытой смены нельзя. Продажа/возврат и закрытие синхронизированы общей транзакционной блокировкой сотрудника. Возврат старого чека учитывается в новой смене и не меняет итог старой.

API: `GET /shifts/current`, `GET /shifts?page=1`, `GET /shifts/{id}`, `POST /shifts` с `{id: UUID, openingCash: decimal}`, `POST /shifts/{id}/close` с `{countedCash: decimal}` под тем же POS-префиксом. UUID открытия сохраняйте при повторной отправке. Повтор продажи с исходным operationId возвращает тот же чек и после закрытия смены.

Внесение/изъятие наличных в течение смены и фискальный Z-отчёт пока не реализованы; экран показывает внутренний кассовый отчёт.

Согласованное в рабочем обсуждении расположение: каталог и поиск слева, чек и оплата справа; оформление существующей панели DADO HOME. Вкладки: продажа, отложенные чеки, история и отчёт. Кассир сразу попадает в POS после входа.

* Цены и названия берутся сервером из каталога; введённые клиентом цены не принимаются.
* Наличные: полученная сумма и сдача. Card/QR: учёт уже подтверждённой на внешнем терминале оплаты, без процессинга платежей.
* Отложенный чек не резервирует товар. При возобновлении цены/наличие проверяются заново; чек нельзя провести дважды.
* Возврат построчный, допускается частичный и полный. Сумма вычисляется по исходной цене. Деньги выдаются кассиром / возвращаются на внешнем терминале; API фиксирует учётную операцию и восстанавливает остаток.
* Печать формирует товарный чек средствами браузера. Интеграция с фискальным регистратором не входит в модуль.
* Отчёт считает продажи по дате проведения, возвраты по дате возврата; границы `[from,to)`, интерфейс использует сутки UTC.

## API

Префикс `/api/admin/pos`, требуется Bearer JWT сотрудника.

* `POST /sales` — провести продажу.
* `POST /held` — создать/обновить отложенный чек.
* `DELETE /held/{id}` — отменить отложенный чек (сохранить историю).
* `GET /receipts?status=Held&page=1` — список, по 50 записей.
* `GET /receipts/{id}` — чек, позиции и история возвратов.
* `POST /receipts/{id}/returns` — возврат позиции.
* `GET /report?from=...&to=...` — финансовый отчёт (максимум 366 дней).

Продажа/откладывание: `{operationId: UUID, items: [{productId: UUID, quantity: integer}], paymentMethod: "Cash"|"Card"|"QR", tendered: decimal, heldReceiptId: UUID|null}`. Для отложенного чека передавайте `tendered: 0`.

Возврат: `{operationId: UUID, lineId: UUID, quantity: integer}`.

Один `operationId` сохраняется для повторной отправки той же операции. Другой запрос с тем же ключом отклоняется. Повтор возвращает актуальное состояние того же чека. После сетевой ошибки интерфейс блокирует изменение операции до получения её результата. Ошибки валидации — 400, запрет прав — 403, недоступный чек — 404, конфликт состояния/остатка/ключа — 409. При конфликте блокировок повторяйте неизменный запрос с прежним ключом.

## Транзакции и безопасность

Продажа блокирует товары `SELECT ... FOR UPDATE` в стабильном порядке. Списание остатков, сохранение чека, ключа идемпотентности и аудита выполняются в одной транзакции. Ошибка любой позиции откатывает всю продажу. Advisory locks сериализуют повторные операции и изменения одного чека. Возврат проверяет оставшееся количество под блокировкой чека, увеличивает остаток атомарным SQL UPDATE и сохраняет аудит в той же транзакции.

PAN/CVV и произвольные платёжные метаданные отсутствуют в DTO и схеме. Неизвестные JSON-поля POS-запросов отклоняются. Секреты не добавлены; конфигурация использует существующий механизм переменных окружения.

Миграция `20260923120000_StorePos` добавляет только таблицы POS, индексы и ограничения. Начальная миграция также получила исправление именованного аргумента `constraints`: в исходном репозитории она не компилировалась. Схема начальной миграции не изменена.

## Проверка

```
dotnet build backend/DadoHome.Api
cd admin
npm ci
npm run build
```

Интеграционный тест `node tests/pos.integration.mjs` запускает backend и проверяет API против настоящей PostgreSQL. Задайте `POS_TEST_CONNECTION` на **отдельную пустую тестовую базу**, при необходимости `DOTNET` — путь к dotnet. Тест генерирует временный JWT-ключ и пароль в памяти, создаёт тестовые записи, завершает backend после проверки. Базу после теста можно удалить.
