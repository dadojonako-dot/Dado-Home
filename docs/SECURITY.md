# Авторизация и ограничения тестовой версии

## Реализовано

* Все JWT проверяются по подписи HS256, issuer, audience, сроку действия и существованию пользователя. Для сотрудников дополнительно проверяются активность, текущая роль и версия сессии в БД. Проверка распространяется на все API, а не только POS.
* Смена пароля, роли, отключение или повторное включение сотрудника увеличивает AuthVersion. Ранее выданные токены получают 401; интерфейс возвращает пользователя на экран входа. Изменение имени без изменения доступа не завершает сессию.
* Старые токены без auth_version перестанут работать после обновления. Пароли и учётные записи сохраняются; достаточно войти снова.
* После 5 неверных паролей учётная запись блокируется на 15 минут. Счётчик и время хранятся в PostgreSQL; конкурентные попытки сериализуются блокировкой строки. Правильный пароль до окончания блокировки не открывает вход. Смена пароля администратором снимает блокировку и отзывает старые токены.
* Вход сотрудников ограничен 20 запросами на 5 минут с IP. Запрос OTP — 10 в час, проверка OTP — 30 за 5 минут. Возвращается 429 с Retry-After при срабатывании IP-ограничения. Произвольный X-Forwarded-For не считается доверенным адресом клиента.
* Новые пароли хешируются PBKDF2-HMAC-SHA256 с индивидуальной солью и 600000 итераций. Старый формат 120000 поддерживается и обновляется после успешного входа. Повреждённый хеш даёт отказ, а не исключение. Пароли и JWT не записываются в аудит; успешный вход фиксируется по ID сотрудника.
* Изменения сотрудников выполняются под общей блокировкой, чтобы параллельные изменения не обходили защиту последнего администратора.
* Демонстрационный или слишком короткий JWT-ключ запрещает запуск. appsettings.json больше не содержит ключа и пароля БД. Windows launcher передаёт локально сгенерированные значения. При самостоятельном запуске задавайте ConnectionStrings__DadoDb и Jwt__Key через безопасную конфигурацию среды.
* Swagger доступен только в Development/Pilot. Production использует HSTS/HTTPS-перенаправление и общий обработчик ошибок без выдачи исключений клиенту.

## OTP и SMS

SMS-провайдер **не подключён**. В Production и Pilot обе OTP-операции возвращают `503 SmsProviderNotConfigured`, без сообщения об отправке и без выдачи кода. Сотрудники входят по паролю; работа кассы от этого не зависит.

Только в Development ответ содержит devCode. Телефон нормализуется в международную форму +… (8–15 цифр, допустимы пробелы/скобки/дефисы во входе). Код живёт 5 минут, доступен для повторной отправки через минуту, допускает 5 проверок и погашается атомарно. Память ограничена 10000 активных записей. Хранилище предназначено только для одного процесса разработки. Параллельные успешные проверки одного кода не создают два входа.

## Что ещё требуется перед production

Нужно выбрать SMS-провайдера и добавить реальную доставку с общим хранилищем одноразовых кодов, сроками и лимитами на стороне БД/Redis. Для нескольких экземпляров приложения IP-ограничения должны дополняться общим ограничением на reverse proxy; текущий IP-счётчик относится к одному процессу (блокировка учётной записи уже общая в БД). Настройте доверенные proxy-адреса при развёртывании — не включайте доверие произвольным forwarded-заголовкам.

Требуются также настройка TLS и домена, хранение/ротация секретов, резервное копирование с восстановлением, мониторинг, политика паролей/дополнительного подтверждения для сотрудников и итоговый аудит безопасности. Эта доработка закрывает перечисленные проблемы авторизации, но не означает завершение полного аудита приложения или готовность платежей.

## Проверки

`tests/security.integration.mjs` запускается с `POS_TEST_CONNECTION` на отдельную пустую PostgreSQL-базу. Проверяет запрет demo-ключа, закрытый Swagger/OTP в Production, отзыв сессий после изменений роли/пароля/активности, сохранение блокировки после рестарта, конкурентные попытки, IP-лимиты и поддельный forwarded-заголовок, нормализацию и однократность OTP, запрет административных API для покупателя.

`tests/pos.integration.mjs` проверяет, что продажи, возвраты, смены и RBAC работают с новой авторизацией. Миграция StaffSessionSecurity добавляет только служебные поля сотрудников, не изменяя чеки и остатки.
